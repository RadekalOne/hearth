# Durable named-session enrollment and revocation

Enrollment remains operator configuration in `HEARTH2_NOTICE_SESSIONS` and the existing private token map. Each entry may additionally specify `expires_at` as an explicit UTC ISO8601 timestamp. Omitted expiry means no time limit; use an explicit expiry for temporary sessions. Existing entries remain compatible.

At startup, and before authentication on each request, the application pins each credential SHA256 fingerprint to its session, principal and recipient in `notice-session-credentials.sqlite3` beside the service data. Raw tokens are not stored there. Receipt/work-record restoration does not reset this separate security database.

Removing configuration or the mapped token permanently disables that fingerprint. Rebinding it to another session, rotating it, aliasing it to a general principal, disabling Hearth 2 or restarting cannot expand its authority. Expiry can be shortened but never extended or removed for that fingerprint. Session principal names remain reserved. Re-enrollment requires a fresh, strong credential and operator configuration. Existing addressed notices remain pinned to the same session/principal; a newly issued credential for that same enrollment can retrieve them.

A configured human may POST an empty JSON object to `/api/hearth2/sessions/{session_id}/revoke`. Normal human authentication and same-origin write checks apply. Controllers, workers and named sessions cannot revoke. This terminally revokes all registered credentials of that session; replay changes no prior retirement record. Rotating to a fresh credential is a new operator-authorized enrollment, not undoing revocation.

Retain the registry AND its `.required` marker across backups and restarts. A missing registry with its marker, an empty/corrupt registry or malformed policy fails closed. Never restore an older registry over current revocation state: rollback of trusted security files is outside this protocol's authority. Removing both trusted security files is an operator reset and cannot be detected by application state alone. Keep the token map and registry in the private service data directory; use strong generated secrets. No shared-service rollout or native-session hook is enabled by this increment.

`test/test_hearth2_session_lifecycle_acceptance.py` imports fresh actual application instances over temporary data and uses ASGI HTTP requests. It proves receipt replay, expiry, human-only revocation, active de-enrollment, alias/cookie/API/MCP denial and unchanged task records with understanding unknown. This is offline application acceptance, not a supervised real TCP/TLS run or production deployment.

Verification: 1,145 offline tests passed (184.561 seconds). Focused tests include restart/receipt replay, revoked and expired acknowledgement denial, live de-enrollment followed by restart, generic/reviewer cookie aliases, missing registry, and partial token-file failure without unintended retirement. See the implementation plan for evidence details. All service processes sharing a registry must use the same enrollment configuration; stop old processes before changing that configuration. Requests already authorized and in flight are not retroactively cancelled by revocation.
