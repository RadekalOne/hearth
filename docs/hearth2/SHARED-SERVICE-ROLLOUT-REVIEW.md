## Rollback and closeout

**Default feature backout, including successful pilot closeout:** revoke/retire A/B/C, remove only the pilot's session/controller token entries and temporary alias, set `HEARTH2_ENABLED=false` and clear pilot role/enrollment configuration, then restart only the verified Memory service on the reviewed registry-aware image. Preserve all registry tombstones/marker, receipt/work record and audit evidence; do not delete their files to make the instance appear clean. Recheck old session REST/MCP/login denials, ordinary-user/agent controls, receipt count/digest and unchanged carrier task. Retire laptop token files; leave no poller/native hook/controller or scheduled work. Bound registry/config changes to this exact pilot, not unrelated users.

**If the new image or auth guard itself is unhealthy:** stop only Memory and use the separately validated registry-aware fallback image with H2 disabled and the newest security state. If no such image has passed or it cannot safely read current security state, keep the affected service in explicit maintenance/fail-closed mode and forward-fix; do not automatically restart the old `762fd5f` or the historical `hearth-memory-1`. This availability tradeoff needs explicit review before deployment. Turning H2 off alone does not remove the shared authentication middleware.

**Data disaster:** keep current state/evidence intact, stop all Memory writers and restore the verified backup to a new private destination. A data restore can lose legitimate writes made after the backup and cannot roll revocations backwards. Preserve/merge the newest security registry and marker under a separately reviewed recovery procedure. Any replay risk, missing current registry, HM data rewind or old-image fallback requires a separate recovery decision; none is authorized by this packet. Never restore the entire pre-pilot volume over newer writes as routine rollback.
